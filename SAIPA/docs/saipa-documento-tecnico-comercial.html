1. Visión y Propuesta de Valor

SAIPA es un ecosistema de acompañamiento pedagógico que se integra a Moodle para mitigar la deserción estudiantil mediante tres pilares: un asistente conversacional con IA, analítica predictiva de riesgo de abandono, y comunicación proactiva por WhatsApp.

Insight pedagógico central: La deserción rara vez es repentina. Se anuncia con semanas de anticipación a través de señales medibles: caída en la interacción, tareas sin entregar, ausencia de acceso a la plataforma. SAIPA detecta esas señales y actúa antes de que sea tarde.

Para el Estudiante

FuncionalidadDescripciónCanal
Tutor 24/7Responde dudas sobre contenidos del curso en lenguaje naturalChat web + WhatsApp
Espejo de progresoMuestra logros, avances y áreas de mejora en lenguaje claroMoodle + WhatsApp
Recordatorio amigableAvisa fechas de entrega con tono cálido y propositivoWhatsApp
Señal de cuidadoConsulta proactivamente si el alumno necesita ayuda tras días de inactividadWhatsApp

Para el Docente

FuncionalidadDescripción
Alerta tempranaSemáforo de riesgo por estudiante con factores explicativos
Panel de conversacionesHistorial de interacciones alumno-IA para supervisión humana
Generación de rúbricasBorradores automáticos basados en objetivos de la cátedra
Resumen semanalEstado de engagement de la clase en un vistazo
Diferenciador clave: WhatsApp tiene una tasa de apertura del 98% vs. el 25% del correo institucional. SAIPA lleva la universidad al lugar donde viven emocionalmente los estudiantes: su teléfono.

2.2 Componentes del Plugin Moodle

PluginTipo MoodleResponsabilidad Principal
local_saipa local Núcleo del sistema: esquema de DB, cron, observadores de eventos, configuración admin, web services REST para comunicarse con el frontend JS y el bridge Python
block_saipa block Widget de chat visible al estudiante en el sidebar del curso. Template Mustache + módulo AMD JS. Muestra historial de conversación y feedback.
message_output_saipa message output Canal WhatsApp integrado en el sistema de notificaciones nativo de Moodle. Permite que cualquier evento Moodle dispare un mensaje WhatsApp al estudiante.

3.3 version.php — Formato Exacto (Moodle 4.4+)

<?php
defined('MOODLE_INTERNAL') || die();

$plugin->component = 'local_saipa';       // frankenstyle: type_name
$plugin->version   = 2026031600;          // formato: yyyymmddHH
$plugin->requires  = 2024042200;          // Moodle 4.4 mínimo
$plugin->maturity  = MATURITY_ALPHA;      // ALPHA → BETA → RC → STABLE
$plugin->release   = '0.1.0';
$plugin->supported = [404, 500];          // Moodle 4.4 hasta 5.0
$plugin->dependencies = [
    'block_saipa' => 2026031600,
];

7. Modelo de Comercialización

7.1 El Modelo Dual: GPL + Propietario

Moodle es GPL v3. Todo plugin que se integre y distribuya hereda esa licencia. Sin embargo, SAIPA tiene una arquitectura de dos componentes con naturaleza legal distinta, lo que habilita un modelo comercial sólido:

Naturaleza legal de cada componente
graph LR
    subgraph GPL["GPL v3 — Libre (plugin PHP)"]
        A["block_saipa\nlocal_saipa\nmessage_output_saipa\n\n→ El cliente puede tenerlo\n→ Pero es inútil sin el motor"]
    end

    subgraph COM["Licencia Comercial — Propietario"]
        B["saipa-engine\n(Python backend)\n\nRAG · Analítica · WhatsApp\n\n→ ESTE ES EL PRODUCTO\n→ Sin licencia válida → no funciona"]
    end

    A -->|"se conecta vía HTTP\n(requiere licencia activa)"| B

    style GPL fill:#fff9c4,stroke:#f9a825,stroke-width:2px
    style COM fill:#e8f5e9,stroke:#2e7d32,stroke-width:2px
Analogía: El plugin PHP es el control remoto (libre, disponible). El backend Python es el televisor (propietario, se licencia). Uno sin el otro no hace nada útil.

7.2 Tres Modelos de Venta

ModeloDescripciónVentajaDesventajaPrecio típico
A — SaaS El backend Python corre en servidores de S&P. La universidad se conecta via API. Máxima protección del código. Ingresos recurrentes. Muchas universidades exigen que sus datos no salgan de su red. USD 200–500/mes
B — On-Premise ✅ El backend corre en el servidor de la universidad. Licencia anual con validación online. Resuelve la objeción de soberanía de datos. Los datos nunca salen de la institución. Requiere que el cliente instale Docker. Soporte técnico más complejo. USD 1.500–3.000/año + USD 2.000–5.000 fee inicial
C — Gestionado S&P instala y mantiene todo en los servidores de la universidad. Contrato de servicio. Máximo valor percibido. Relación más profunda con el cliente. Mayor carga operativa para S&P. USD 3.500–8.000/año (todo incluido)

Modelo recomendado: B (On-Premise con Licencia) — resuelve la principal objeción de universidades latinoamericanas (soberanía de datos) y genera ingresos recurrentes anuales predecibles.
